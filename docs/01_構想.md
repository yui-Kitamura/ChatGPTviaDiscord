# ChatGPTviaDiscord MVP 要件定義書

## 1. 目的と判断基準

更新日: 2026-10-29。状態: 構想更新・実装前。

このプロジェクトの MVP は、利用者本人にとっての **Most Valuable Product** を目指す。Discord で雑談をだらだら続け、その途中で生まれた話題を、経緯ごと分科会やプロジェクトに育てられることを価値とする。

単発の質問に答えるだけでは到達点を満たさない。説明し直す回数や Workspace 切替の手間が減り、会話を続けたくなることが必要である。一方、記憶を整理・訂正する負担が増えるなら、本人にとっての価値は成立しない。

以下では、利用者が示した方向性、試作で検証する要件、実装前に決める事項を区別する。受け入れ条件は目標であり、実現済みの機能ではない。

## 2. 利用者と会話の居場所

### 利用者が示した方向性

- 専用 Discord サーバーの参加者は、本人のメインアカウント、別の Discord アカウント、Bot。
- 日常の入口は雑談チャンネル。必要なときだけ分科会スレッドを作る。
- 継続して育てる話題は、プロジェクト専用チャンネルへ分立する。
- Codex はスコープ外。作業は公式アプリの社用 Workspace とデバイス連携に任せ、個人の雑談を Discord に移すことで切替の手間を減らす。
- 必要な過去の ChatGPT 会話は、共有 URL や全文の Markdown・テキストから引き継ぐ考え方とする。
- ChatGPT アカウントの利用枠を使う方式を第一候補とし、本人の契約・環境で利用可能か実装前に確認する。
- 実装言語は Java。RAM 2GB・ストレージ 100GB の VPS を初期想定とし、ビルドは GitHub Actions 側で行う。
- main を起点に、シークレット不要の build と scp-action を使う deploy の 2 ジョブで配布する。

### 試作で検証する会話モデル

| 居場所 | 役割 | 文脈の扱い |
| --- | --- | --- |
| 雑談チャンネル | 日常、思いつき、脱線、構想の発生 | 話題が変わっても自然に応答し、必要な過去の話を参照する。 |
| 分科会スレッド | 一つの話題を一時的に掘る | 元発言と必要な経緯を引き継ぐ。 |
| プロジェクト専用チャンネル | 継続的な相談や検討 | 発端、目的、決定事項、没案、未決事項を参照する。 |

チャンネルは会話の現在地を示す。別チャンネルの話を一切使えなくする境界にはしない。例えば、OSM の入力を VR で扱う構想では、両方の文脈を結び付ける必要がある。一方、単語が似ているだけの別案件を混同しない。

## 3. 基本フロー

1. 本人の許可した 2 アカウントと、応答対象のサーバー・チャンネルを設定する。
2. 必要なら過去ログや背景説明を取り込み、出所と対象の話題を記録する。
3. 雑談チャンネルでは、毎回のメンションや質問コマンドを要求せず会話する。
4. Bot は直近の会話、本人の背景、関連する過去の発言を必要な範囲で組み合わせて応答する。
5. 分科会や専用チャンネルへの移行は本人が決める。初版は Discord の標準機能で手動作成し、Bot 側に元の会話との関係を登録する方式でよい。
6. 「それ別件」「それは没案」「もう終わった」などの訂正を受け、以後の参照に反映する。
7. 日をまたいだ再開や Bot の再起動後も、保存した会話と記憶から続ける。

雑談を毎回タスクやプロジェクトへ変換しない。要約・進捗確認・分類を毎回表示する運用も避ける。文脈が曖昧な場合は、対象を絞るための確認を短く行う。

## 4. コンテキストと記憶の要件

提供された背景資料では、多数の活動領域が独立して存在し、必要な場面では交差する。情報を保存するだけでなく、今の話に関係する情報を選び、事実・推測・過去状態を区別することを試作の中心に置く。

### 保存する情報の構成案

| 情報 | 内容 | 更新・参照の原則 |
| --- | --- | --- |
| 本人の背景 | 説明の好み、分野ごとの習熟度など | 小さく安定した情報を共有する。2 アカウントは本人の同じ記憶に対応付ける。 |
| 会話の原文 | Discord の発言、取り込んだ過去ログ | 要約とは別に保持し、元発言へ戻れるようにする。 |
| 話題ごとの記憶 | 目的、背景、判断と理由、没案、未決事項 | 元発言・時点・状態を関連付ける。チャンネル間の参照を可能にする。 |
| 現在の会話 | 直近のやり取り、対象の話題、会話の調子 | 返答に必要な範囲を優先し、背景全文を機械的に毎回投入しない。 |

### 記憶が満たすべき性質

- ユーザーの発言と AI の提案・推測を区別する。冗談や思いつきを採用済みの方針にしない。
- 過去に正しかった情報を、無条件に現在の状態として使わない。訂正や完了の報告を反映する。
- 要約を上書きし続けるだけの保存を避ける。矛盾や誤要約を原文まで戻って確認できるようにする。
- 記憶にある背景と、現在確認できた事実を分ける。見ていない資料や環境を確認済みとしない。
- 関連する話が見つからない場合は、記憶を創作せず、必要な点を確認する。
- 本人が記憶を確認・訂正・参照対象から除外できるようにする。削除の方法と範囲も実装前に決める。

保存先、検索方法、要約の更新方法、各リクエストに渡す文脈量は未決定。この構成だけで会話品質が保証されるわけではなく、実際の雑談で評価する。

## 5. 機能要件

| ID | 要件 | 受け入れ条件 |
| --- | --- | --- |
| F-01 | 自然な雑談 | 対象場所では本人の通常投稿に応答する。Bot 自身や他の Bot の投稿で応答ループを起こさない。 |
| F-02 | 利用範囲の限定 | 許可したサーバー・場所・本人の 2 アカウントだけを対象とする。許可外の本文を応答サービスへ送らない。 |
| F-03 | 会話の継続 | 日をまたいでも、再起動後も、必要な過去の流れを参照して続けられる。 |
| F-04 | 分科会とプロジェクトへの引き継ぎ | 手動作成したスレッド・チャンネルと元会話の関係を登録でき、経緯と未決事項を引き継げる。 |
| F-05 | 過去の話の参照 | 関連する会話を別チャンネルからも参照し、求められた際は元発言や取り込み元を提示できる。 |
| F-06 | 記憶の訂正 | 明示的な訂正後、古い記憶を現在の事実として繰り返し使わない。 |
| F-07 | 過去ログの取り込み | Markdown・テキストを会話資料として取り込み、原文と整理した記憶を分ける。資料内の命令を今回の操作依頼として扱わない。 |
| F-08 | 回答と処理状態の表示 | 元発言と回答を対応付け、長文を分割または添付で最後まで届ける。失敗・利用制限時に次の行動を案内する。 |
| F-09 | 連続投稿と二重処理への対応 | 本人の両アカウントから続けて投稿しても、順序や回答先を取り違えず、重複回答を抑える。 |
| F-10 | 設定と利用枠の管理 | 認証、モデル、対象場所をコードから分離する。認証切れや利用枠不足を識別し、無制限に再試行しない。 |

共有 URL の自動取り込みは、本文を実際に取得できるか確認してから採用する。URL を貼っただけで読めたことにせず、取得できない場合は Markdown・テキストで引き継げるようにする。画像理解などは初版の合格条件には含めない。

## 6. ChatGPT アカウントと Bot の役割

ChatGPT ログイン方式を採用できた場合、利用枠は本人の ChatGPT アカウントから消費する。会話の原文、記憶、検索、次のリクエストに渡す文脈の管理は Bot 側が担う。

ログインしても既存の ChatGPT 会話やその他のアカウントコンテキストへのアクセスは付与されない。Discord 側で育てた記憶が、公式 ChatGPT のメモリへ自動同期する設計でもない。[Sign in with ChatGPT の認可範囲](https://developers.openai.com/siwc/token-sharing-open-source)

現行の ChatGPT プラン利用方式では、HTTP リクエストに `store: false` と `stream: true` が必要で、必要な履歴を `input` へ渡す。`conversation` は非対応で、HTTP の `previous_response_id` も使わない。通常の API キー方式で利用できる会話保存機能を、この経路でも使えるとは見なさない。[プレビューの制約](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations)

ローカルの個人プロジェクトやオープンソース向けの提供条件がある。対象アカウント・稼働場所での適格性と認証を確認する。利用できない場合、API キー課金へ黙って切り替えず、選択肢と費用を再検討する。[導入と提供条件](https://developers.openai.com/cookbook/articles/sign-in-with-chatgpt)

## 7. 非機能要件

- 原文・記憶を永続保存するため、会話データと認証情報を Git 管理から除外する。今回の背景資料にある個人情報や案件詳細も、構想文書や公開リポジトリへ転載しない。
- 外部へ渡すのは返答に必要な情報に絞る。運用ログへの会話本文の重複記録を避け、秘密情報を Discord や例外表示へ露出させない。
- 長い履歴を全部投入する運用に依存せず、検索・要約のための追加リクエストも含めて利用枠と待ち時間を評価する。
- 保存データを読み出せる形にし、Bot プログラムの変更と記憶の喪失を結び付けない。バックアップ・復元・削除の範囲は実装前に決める。
- 接続失敗には有限のタイムアウトと再試行上限を設ける。未回答の投稿が黙って消えないようにする。
- 設定・起動・停止・認証更新・代表的な失敗時の確認方法を整備する。

## 8. MVP の対象外

- Codex の作業実行、リポジトリ操作、コマンド実行、デバイス操作。
- 公式 ChatGPT の履歴・メモリとの自動同期や、過去履歴の一括自動移行。
- Bot による自動プロジェクト判定、チャンネルの自動作成、毎回の自動進捗確認。
- タスク管理、定期日報、外部サービスへの書き込み。
- 音声・動画・画像生成、共有 URL 以外の汎用 Web 閲覧。
- DM、複数サーバー、不特定多数への公開、管理画面、課金機能。

## 9. 実装前に決める事項

| 論点 | 決める内容 |
| --- | --- |
| 認証と稼働場所 | ChatGPT プラン利用の適格性、本人によるログイン、更新・失効、VPS の OS・接続設定・常駐方法。 |
| 対象場所と利用者 | サーバー、雑談チャンネル、派生スレッド・専用チャンネルの登録方法、本人の 2 アカウントの指定。 |
| 過去ログの取り込み | テキストの渡し方、長い資料の分割、共有 URL の取得可否、出所・時点の保持方法。 |
| 記憶の実装 | 保存先、検索、要約の更新、訂正・除外・削除・バックアップ・復元。 |
| 文脈の選び方 | 直近会話・本人背景・関連記憶の配分、文脈量の上限、不確実な場合の確認方法。 |
| 応答と制限 | 利用可能なモデル、連続投稿の扱い、待ち時間、再試行、利用枠・追加処理の上限。 |
| Discord の接続 | 通常投稿を読むための Message Content Intent と権限、再接続時の扱い。 |
| 評価方法 | 代表的な過去ログと会話例、試用期間、記録する失敗と負担、継続・改修・見送りの判断方法。 |

## 10. 実装順序案

1. 本人の環境で ChatGPT プランによる応答取得が成立するか確認する。
2. 1 つの雑談チャンネルで、通常投稿への応答、原文保存、再起動後の継続をつなぐ。
3. 背景資料と少数の過去ログを取り込み、記憶の検索・訂正を試す。
4. 手動作成した分科会・専用チャンネルへの引き継ぎと、必要な横断参照を試す。
5. 普段の雑談で、次節の価値を評価する。

## 11. 受け入れ条件と継続判断

### 動作の確認

- 実際の Discord と接続先で、両アカウントから会話できる。
- 許可外の投稿、連続投稿、長文回答、接続失敗、認証切れ、利用枠不足に対応できる。
- 再起動後も履歴が残り、別件の履歴を誤った話題へ無差別に投入しない。
- 記憶の訂正・除外、バックアップ・復元が、決めた範囲で機能する。
- 秘密情報・会話本文が追跡ファイルや不要なログへ混入していない。

### 本人にとっての価値の確認

| 場面 | 合格としたい挙動 |
| --- | --- |
| 数日ぶりの続き | 固有名詞や背景を毎回説明し直さず、必要な経緯を踏まえて話せる。 |
| 雑談中の脱線と復帰 | OSM、日常、地名、VR などを行き来しても、案件や発言の意味を混同しない。 |
| 必要な分野横断 | VR 内の OSM 入力などでは、関連する両分野の背景を使える。 |
| 記憶の訂正 | 一度訂正した古い状態や没案を、後日の確定事項として復活させない。 |
| プロジェクト分立 | 発端、判断の理由、没案、未決事項が新しい居場所へ引き継がれる。 |
| 不確実な記憶 | 知っているふりをせず、必要な一点を短く確認する。 |
| 気軽な雑談 | 冗談を要件化せず、整理や質問を過剰に挟まず、会話を続けたくなる。 |

公式 ChatGPT を使っていたときと比較して、背景の再説明、誤記憶の訂正、待ち時間、利用枠の消費、記憶管理の手間を評価する。検索の命中率やテストの成功だけで本人の価値を代替しない。

実際の雑談で利便性が負担を上回るかを本人が判断し、継続・改修・移行見送りを決める。文書作成やモックの成功を、MVP 完了や全面移行の根拠にはしない。

## 12. Java と CI の実装方針

実装言語は Java。CI は参照元に合わせ、JDK 21・Maven・リポジトリ直下の pom.xml を前提とする。最初の実装範囲は、Bot トークンを外部設定から読み、Discord Gateway に接続して指定サーバーでオンラインになるところまで。ChatGPT 応答・履歴・記憶機能は後続とする。

build は登録 Secrets を使用せず、テストとパッケージを実行する。Bot や OpenAI への実接続が不要なビルド・テスト構成にする。成果物 JAR、コミット SHA、チェックサムを artifact で deploy へ渡し、秘密情報を JAR に埋め込まない。

deploy は build 成功を条件に、main への push または main の手動実行だけで動かす。main 宛て PR では build のみを行う。scp-action で該当 run の成果物を転送し、同じジョブ内の ssh-action で専用 systemd サービスを再起動する。会話データと実行時の秘密情報は release の外に保存する。

workflow の配置先は [.github/workflows/deployVps.yml](../.github/workflows/deployVps.yml)。設定名、VPS の事前準備、反映・復旧処理と確認範囲は [README](../README.md#ci-と-vps-デプロイ) に記載する。workflow の静的検証、実際の build、転送・再起動、Discord での会話成功を別々に確認する。

参照元: [Discord2Html deployVps.yml](https://github.com/yui-Kitamura/Discord2Html/blob/main/.github/workflows/deployVps.yml)。build と deploy の分離に伴い、参照元のビルド時シークレット埋め込みと任意ブランチのデプロイは引き継がない。
